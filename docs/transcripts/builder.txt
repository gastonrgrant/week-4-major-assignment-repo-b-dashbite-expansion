[STUDENT]

explain the important implementation decisions you made in very simple language

---

[AGENT]

The container already matched the plan, so the only behavior change was how it stops.

Docker stops a container by signaling the first process inside it. That process used to be `runuser`. `runuser` got the signal and killed the worker immediately. The worker never got to finish the batch it was writing.

The entrypoint now does three things, in order:

1. It starts as root just long enough to create `/data` and give that folder to the `dashbite` user. A normal user cannot do that on a fresh Docker volume.
2. It sets the home directory to `/home/dashbite`. Otherwise the app would try to write under `/root` and fail.
3. It replaces itself with the real command (`simulator`, `preprocess`, `train`, `infer`, or the dashboard), running as `dashbite`. There is no extra program left in front. Docker's stop signal goes straight to that command, the command finishes its current pass, and then it exits.

The five programs still only share files on `/data`. Nothing was added between them. `make run` without Docker was left as it was.

The heartbeat belongs to the demo's programs, not to a courier.

DashBite here is a small pipeline: one program writes orders, another cleans them, another trains, another scores, and a page reads the results. Those programs keep running in containers. Docker cannot tell a live loop from a stuck one just because the container process still exists.
